# Почему события, а не только Camel + DWH (целевое сравнение)

## Как сейчас (наследие, по кейсу)

- **Apache Camel (ESB)** — преимущественно **точечные** интеграции, оркестрация «A вызвать B»; **бизнес-смыслы** часто **теряют** явные границы в **длинных** цепочках преобразований, сложно масштабировать при росте **числа пар** N×M.  
- **DWH (MS SQL Server) + ETL-логика** — **центр тяжести** отчётов и, исторически, **бизнес-правил**; длительные **сроки** вывода изменений при появлении **новых направлений**; batch в часах.

## Куда целимся (требования задания и C4 Task3)

- **Event Backbone** + **Ingestion** с **контрактами** и **политиками** — **асинхронная** доставка **смыслов** (domain events) без **жёсткого** связывания продьюсеров с консюмерами.  
- **Data Products** (поток + lakehouse) — **вынесение** логики **из** монолитного DWH, но с **мостом** (Camel/DWH) на переход.  
- **Data Access & Governance** — **соблюдение** self-service-ограничения (медкарта, анамнез, **результаты** — не в портале), через **классификацию** и RLS, а не через **ручной** ETL-набор.

## Сравнение (кратко)

| Критерий | «Только» Camel + DWH | Целевой EDA + data products (и ACL легаси) |
|----------|----------------------|--------------------------------------------|
| **Связываемость** | Рост N×M интеграций, сложно менять | **pub/sub** по **контрактам**; **нового** подписчика подключают, **не** перестраивая **целиком** цепочки **существующих** пар. |
| **Time-to-market** | Новая метрика → часто ETL+зависимости+окна | Новый **consumer** / **топик**-подписка, **независимые** релизы доменов. |
| **Масштабирование** | Очереди и БД в центре | **Партиционирование** потока, **горизонталь** для обработки и **near-real-time** (целевой горизонт 3 года). |
| **Согласованность** | Согласованный срез в витринах **после** пакетной загрузки (задержка в часах) | **Eventual** + **явные** `eventId`/`occurredAt` + idempotent consumers + **DLQ** (Task3). |
| **Гибкость продуктов** | Сложно изолировать домены | **Границы** bounded contexts, **anti-corruption** к DWH, а не **один** сквозной **монолитный** ETL-конвейер. |
| **ИБ/комплаенс (PHI, банк)** | Риск **слишком широкого** ETL-извлечения | **Min payload** + **теги** + **governance** до self-service, **сегментация** топиков. |

**Реакция / скорость смены курса (по формулировкам задания):** события позволяют **асинхронно** вовлекать новых подписчиков (в т.ч. **ИИ** и **финтех**) **без** снятия нагрузки **целиком** на пакетный DWH; легаси-**синхрон** остаётся **временным** мостом, а **не** архитектурным центром.

**Итог:** EDA + контракты + governance — практичный **ответ** на **две** задачи руководства: (1) self-service с **предсказуемыми** границами, (2) подключение **направлений** без **добавления** **основного** **объёма** логики **в** DWH, как в формулировке задания.
