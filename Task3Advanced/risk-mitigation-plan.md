# План управления рисками

В таблицах нет колонки «Владелец / ответственный»: в исходном кейсе не задана оргструктура. Для задания 3 достаточно мер снижения и разделения на технологические и управленческие меры, как в условиях курса.

## Технологические меры


| Риск | Меры снижения                                                                                                                   | Горизонт |
|------|---------------------------------------------------------------------------------------------------------------------------------|----------|
| R1   | Планирование ёмкости для событийной шины, нагрузочные тесты, лимиты на consumer groups, горизонтальное масштабирование брокеров | 0-12 мес |
| R2   | Anti-corruption layer для legacy DWH/Camel, единый каталог бизнес-правил, декомпозиция ETL по доменам                           | 0-18 мес |
| R3   | Schema Registry с версионированием, контрактные тесты producer/consumer, управление несовместимыми изменениями                  | 0-12 мес |
| R4   | Сквозная трассировка, технические метрики backlog/lag/retry, обязательный DLQ + replay-процедуры                                | 0-12 мес |
| R7   | Классификация данных, шифрование при хранении и передаче, сегментация контуров PHI/финтех, policy-as-code                       | 0-36 мес |
| R8   | План вывода из эксплуатации Camel с KPI миграции, приоритезация критических интеграций на события                               | 6-36 мес |


## Управленческие меры


| Риск | Меры снижения                                                                                                                 |
|------|-------------------------------------------------------------------------------------------------------------------------------|
| R5   | Программа обучения DDD/EDA, архитектурные комитеты, шаблоны ADR и чек-лист ревью                                              |
| R6   | Назначение Data Product Owner в каждом домене, RACI на data contracts, регулярный междоменный governance council              |
| R2   | Контрольные точки этапов миграции с метриками качества данных и времени отчётности                                            |
| R7   | Регулярные security/compliance-ревью, аудит доступа и обязательные тренировки реагирования на инциденты (tabletop-упражнения) |


## Контроль и пересмотр

- Периодичность пересмотра риск-реестра: 1 раз в квартал.
- Эскалация: риски с влиянием `Высокое` и статусом `без прогресса > 1 месяц`.
- Основные KPI: задержка потоков, доля контрактных нарушений, MTTR, доля доменов с назначенным Data Product Owner.
