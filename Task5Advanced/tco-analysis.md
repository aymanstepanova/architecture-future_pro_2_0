# TCO-анализ на 3 года

Расчет показывает порядок затрат для архитектурного выбора, а не коммерческое предложение конкретного облачного провайдера. Единица оценки - **млн руб. в год**. Сравнение строится для двух сценариев:

- **Текущая архитектура:** MS SQL Server 2008 DWH как центр данных и бизнес-логики, PowerBuilder, кастомизации Power BI, Apache Camel, batch-отчетность.
- **Целевая архитектура:** cloud data lakehouse, событийная платформа, доменные data products, self-service BI, governance, Terraform/CI/CD, ACL для легаси на период миграции.

## Основные допущения

| Допущение    | Значение для модели                                                                                                                                                        |
|--------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Рост данных  | Сотни ТБ уже сейчас; в горизонте 3 лет рост источников, продуктов и регионов повышает нагрузку на DWH и batch-ETL.                                                         |
| Легаси       | В текущем сценарии DWH/Camel продолжают быть центральными системами; стоимость поддержки и изменений растет.                                                               |
| Миграция     | В целевом сценарии первые 12-18 месяцев дороже из-за платформенной команды, обучения, параллельной работы легаси и новой платформы.                                        |
| Self-service | В целевом сценарии снижается ручной труд аналитиков и DWH-разработчиков за счет повторно используемых data products и semantic layer.                                      |
| Безопасность | Медицинские карты, истории болезни и сырые результаты исследований не включаются в self-service; затраты на governance и обезличивание считаются частью целевой платформы. |

## Итоговая экономика

| Показатель | Текущая архитектура | Целевая архитектура | Вывод |
|------------|---------------------|---------------------|-------|
| TCO за 3 года | 1085 | 1020 | Целевая архитектура дешевле на 65 млн руб. за счет снижения run-rate после миграции. |
| Run-rate в год 3 | 405 | 270 | Экономия на стабильной эксплуатации: 135 млн руб. в год. |
| Основной пик затрат | Нет отдельного пика, но стоимость растет ежегодно | Год 1 из-за миграции и параллельной эксплуатации | Инвестиции окупаются через снижение поддержки, ручного труда и риска легаси. |
| Скорость изменений | Низкая: логика в DWH и batch-ETL | Выше: доменные data products и события | Улучшает time-to-market для новых финтех-, мед- и AI-продуктов. |
| Масштабирование регионов | Дорогое и централизованное | Управляемое через домены, облако и data contracts | Лучше соответствует цели выхода в 2-3 региона. |

## Качественные выгоды, не полностью отраженные в TCO

- Сокращение времени подготовки отчетов: от часов и ручных заявок к near-real-time витринам там, где это нужно бизнесу.
- Снижение риска регуляторных нарушений за счет классификации данных, RLS/CLS, псевдонимизации и policy checks.
- Более быстрый запуск новых направлений: фарма, медоборудование, новые финтех-продукты подключаются через data contracts и события, а не через доработку центрального DWH.
- Уменьшение зависимости от редких легаси-компетенций SQL Server 2008, PowerBuilder и монолитных batch-процессов.

## Риски TCO и контроль

| Риск                                         | Как контролировать                                                                                          |
|----------------------------------------------|-------------------------------------------------------------------------------------------------------------|
| Облачные расходы могут вырасти быстрее плана | FinOps-процессы, бюджеты по доменам, autoscaling, lifecycle policies для storage.                           |
| Параллельная эксплуатация легаси затянется   | KPI миграции по доменам, дедлайны вывода Camel/DWH с критического пути, quarterly architecture review.      |
| Data Mesh превратится в дублирование команд  | Единая platform team, шаблоны data product, общий каталог, повторное использование pipeline-компонентов.    |
| Экономия времени аналитиков не реализуется   | Метрики adoption self-service, число ручных заявок, freshness/SLA data products, обучение BI-пользователей. |
